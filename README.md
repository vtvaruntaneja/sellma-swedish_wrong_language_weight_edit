# Does a small weight edit stop wrong-language replies to Swedish prompts?

This is my take-home assignment for SE.LLMA (WASP). It has two parts:

1. A critique of the blog post
   ["Sparks of Weight-Space Programming"](https://rikiyat.github.io/blog/weight-space-programming/).
2. An experiment: can a small, targeted weight edit stop Qwen2.5-0.5B-Instruct from answering Swedish prompts in
   Norwegian, Danish or English?

**Short answer: no.** The edit did no better than random edits of the same size. A Swedish system prompt and a small
fine-tune helped more, but each had a cost.

- `NOTE.md`: the research note (about 2 pages).
- `report.pdf`: the two-page report (sections 1-7 of `NOTE.md`, without the appendix). All results tables are in `results/summary.md`.
- `results/summary.md` and `results/summary.json`: all the numbers, generated by `analyze.py`.
- `AI_USAGE.md`: how I used AI tools.

The edit is the kind the blog's Experiment 8 used. I found it from the model's activations (its internal values
while it reads a prompt) and chose it using feedback on development prompts. It was not read off the weights.

## How to reproduce

You need an Apple-silicon Mac (the code uses MPS, Apple's GPU backend) and Python 3.11. Package versions are pinned
in `requirements.txt`.

```
./run.sh            # everything; writes results/
./run.sh --quick    # smoke test: 10 dev prompts per set; writes results_quick/; never reads a test file
```

`run.sh` runs these steps in this order. All outputs go to `results/`.

| Step | What it does | Main outputs |
|---|---|---|
| `data.py` | builds `data/` from `data/source/*.tsv` and wikimedia/wikipedia | `data/*.jsonl` |
| `experiment.py langid` | checks lingua (the language detector) on labelled paragraphs | `langid_check_summary.json` |
| `experiment.py pilot` | 40 Swedish dev prompts on Qwen3.5-0.8B and Qwen2.5-0.5B-Instruct | `pilot_*_summary.json` |
| `experiment.py dev128` | dev round 1 at 128 tokens: base run, direction, 8 settings | `dev_selection.json` |
| `experiment.py base512` | base model on the dev prompts at 512 tokens | `dev512_base_summary.json` |
| `experiment.py dev512` | dev round 2: 8 settings, selection, English check, diagnostics | `dev512_selection.json`, `dev512_diagnostics.json` |
| `experiment.py lora --skip-dev-eval` | LoRA baseline trained on dev prompts only | `lora_summary.json`, `lora_adapter/` |
| `experiment.py test` | every condition on the test sets, once | `test_*.jsonl`, `test_config.json` |
| `analyze.py sheet` | blinded sheet for the hand annotation | `understanding_sheet.jsonl` |
| `analyze.py` | metrics, paired tests, examples | `summary.json`, `summary.md`, `examples.md` |
| `analyze.py note` | fills the tables and the appendix in `NOTE.md` | `NOTE.md` |

**One step is not code.** `results/understanding_labels.jsonl` was written by Claude, not by a script. For each
non-Swedish reply, it records whether the reply understood the prompt and whether lingua's language label is right.
Claude followed `results/understanding_rubric.md`. If the replies are identical, a fresh `analyze.py sheet` gives
the same items to label.

If a step stops halfway, run it again with `--resume`. It reuses any generation file that is already complete.

The full run took several hours on my M2 MacBook Air (16 GB). The test step alone took 97.6 minutes. LoRA training
at 512 tokens is slow and needs a lot of memory on a 16 GB Mac.

I made `report.pdf` from sections 1-7 of `NOTE.md` with pandoc and Chrome's headless print, trimming a few repeated sentences to fit two pages.
I checked the code with pyflakes 4.1.0, vulture 2.16 and pylint 4.1.4 (its duplicate-code check). These tools are not
in `requirements.txt`, because the experiment itself does not need them.

## Changes from the original plan

These are the places where the run differs from the plan I started with.

- **Model.** Qwen3.5-0.8B gave no wrong-language reply to 40 pilot prompts in the first 128 tokens, so I used the
  plan's backup model, Qwen2.5-0.5B-Instruct.
- **Pilot decoding.** The Qwen2.5 pilot used the repo's default repetition penalty of 1.1 by mistake. All later runs
  use plain greedy decoding.
- **Two development rounds.** Round 1 followed the plan: 128-token replies and a Swedish-minus-English direction,
  used because there were only 18 failures, fewer than the 20 the plan needed. Removing that direction did not make
  replies more Swedish. In layers 16 to 19 it made almost every reply English. So I ran a second round with
  512-token replies, a rule that both halves of a reply must be Swedish, the Swedish-minus-English direction made
  stronger, and a "wrong-language minus Swedish" direction removed or flipped. The feedback budget counts both
  rounds.
- **Test-set use.** The first version of `--quick` read the first 10 items of every test file. The main analysis
  leaves those items out, and `--quick` now reads development files only.
- **Random control.** 5 random directions instead of 3, decided before the test run.
- **LoRA development check not run.** After LoRA finished training and saved its adapter, the process stalled with
  memory full during its development check, and I stopped it. Training had finished: all 54 steps are logged, and
  the adapter was saved after them. Claude wrote `results/lora_summary.json` by hand from the step log, the adapter and
  the file times, and the file says so. `run.sh` passes `--skip-dev-eval`, so the code matches what I ran.
